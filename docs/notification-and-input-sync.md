# 通知、撤回与输入设置

Telegram 拦截未授权请求后，告警使用「🚨 访问控制通知：来自电报端的未授权请求 🚨」标题。系统先独立保存访问日志，再明确解析 Bot 当前对话，将告警保存为系统记录并同步到 Web。告警会进入该对话的后续上下文，拦截本身不会执行用户命令或调用模型，也不会占用该对话的执行槽。

Web 正在查看其他对话时会显示简短提醒，不切换页面或把告警写入另一个对话。没有选择 Bot 对话时，访问日志与 Telegram 通知仍保留，Web 显示提醒；系统不会猜测应写入哪个对话。静默模式和原有陌生人回复文案保持原设置。

网页用户消息在异步投递前携带持久记录 ID，Telegram 投递成功后将实际消息 ID 回填到对应记录中。长文本的各个片段均关联到同一条记录，CLI 队列中继也保留关联。Web 撤回时沿用已有机制删除这些准确 ID；未送达的消息会被撤回状态阻止补投，撤回与投递同时发生时，迟到的发送结果也会被删除。旧记录若没有保存消息 ID，无法仅凭文本可靠补删。

附件消息收到持久化确认后即可显示分支和撤回操作，刷新前后保持一致。撤回时将原文字、附件与服务器上传引用保存到已有的服务器草稿中；图片和视频在输入区通过服务器地址预览，不转成本地 File 对象，不重新上传。删除草稿里某个附件只移除引用，不删除服务器原件；修改会核对草稿版本与会话归属。

重新发送沿用原文件路径，保持「附件内容」与「服务器上传仅提供路径」的原有区分。Bot 收到的是原文件文档，图片与视频也保留原始字节和文件名。队列重发、旧文本入口与 CLI 中继都按新记录中的附件引用同步；恢复附件与新增文件的混合发送会处理两类文件，而不是只处理新上传的部分。

图片、视频、其他附件和服务器上传按原来的选择顺序显示并发送，移除某张预览只取消该引用。新增文件接在仍保留的恢复附件后。说明文字仍放在首个文件的图注中；超过 Telegram 图注长度时分成相邻文字消息，每段说明和每个文件都关联到同一条新记录。

重新投递的消息建立新的 Telegram 关联，不复用原消息的投递 ID。队列重发把原文件路径送入原有出站通道，网络等待不阻挡网页生成，断线恢复后按顺序补发。再次撤回会删除新文件和说明；等待投递的操作会被撤回状态阻止，正在上传的文件返回后按准确 ID 删除。所有判断继续按会话归属进行，其他对话的消息不参与删除。

原件缺失、无法读取或超过原有 Bot 平台发送上限时明确提示，保留网页记录与原说明；不会重新下载原件到浏览器或把它当成已同步成功。云端与本地 Bot API 的既有容量、超时和大文件发送机制保持不变。

输入框的「生成选项」使用紧凑按钮网格，每项一个按钮：回复方式、工具调用方式、Agent 开关、Agent 轮数和记忆深度。点击后选择或输入数字，数字通过「保存」确认；保存失败保留输入和消息草稿。模型与思考选择仍使用原入口，底层模型请求和执行规则不变。

AI 署名中的品牌头像固定为 24×24 px，名称为 15 px 加粗亮色，两者垂直居中；正文、用量和模型文字保持原样。

验证使用临时数据库、模拟 Telegram/模型与本地隔离浏览器，不包含服务器部署或真实客户端验收。
